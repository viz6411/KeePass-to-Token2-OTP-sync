ROOT CAUSE SUMMARY (FIX FOR 0x6FFB HARDWARE ERROR DURING DIRECT WRITE)
--------------------------------------------------------------------------------
1. In src/t2_kpxc_sync/token2/transport.py, the USB sequence counter `self._seq`
   was persisting across distinct APDU commands sent via `send_apdu()`.
2. When the user initiated synchronization:
   - APDU 1: `list_entries()` was executed. Its 1st chunk was sent with `seq = 0`.
     Upon completion, `self._seq` incremented to 1.
   - The user confirmed the sync plan (e.g., Add Only).
   - APDU 2: `write_entry()` was called, executing `get_token_public_key()`.
     Its 1st chunk was sent with `seq = 1` because `self._seq` was not reset!
   - Real Token2 hardware strictly checks `seq == 0` on the first chunk of a new APDU.
     Because `seq == 1`, the firmware rejected the frame with status word `0x6FFB`.
3. Resolution:
   - `BaseTransport.send_apdu` strictly resets `self._seq = 0` per APDU transfer,
     and each chunk uses `(flag & 0xF0) | (idx & 0x0F)`.
   - Response reassembly checks `rx_seq == expected_rx_seq` starting at 0.
   - `MockHIDTransport` and `VirtualHIDDevice` (conftest.py) now enforce the same
     rule and return `0x6FFB` on unexpected sequence numbers, simulating physical hardware.
